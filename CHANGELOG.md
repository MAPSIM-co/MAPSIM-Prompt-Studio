# Changelog

## 2.2 — a Persian interface, bilingual analysis and a model picker that explains itself
- The engineered output card is now two complete halves. The Persian half carries the Persian prompt, the Persian purpose and all four analysis groups in Persian; the English half carries the same sections in English. Each half has its own copy button and its own expand control.
- `persian_analysis` is part of the compile contract: the model mirrors `detected_purpose` and the four analysis arrays item for item. When a response omits or truncates the mirror, `prompt_compiler.prompt_engine.mirror_analysis` fills the gaps from the English items, so the Persian half is never blank while the English half has content. Older library entries and an older server are handled the same way in the browser.
- Enlarged both prompt boxes: a comfortable reading height that grows with the viewport, its own scroll area, and an expand control that releases the cap.
- Every label, message and error the operator can see is Persian — including provider failures, which now name the model and say what to check.
- The model pickers explain themselves: usable models and unusable models are separate groups, each option carries its class in Persian (`سبک (Lite) — ارزانترین`), every option tooltip and the panel under the picker give class, speed, cost tier, best use and the recorded RPM/TPM/RPD ceilings, and cost links to Google's official pricing page instead of invented prices.
- The settings modal is three numbered blocks. The API-key block documents where the key is stored, environment precedence, masking and rotation. The model block answers «چطور بهترین مدل را انتخاب کنم؟». The optional system-prompt block explains what an override replaces, gives four patterns worth writing, inserts a contract-safe sample and warns that dropping the output keys breaks parsing.
- Library search now reads the Persian analysis text, so a Persian phrase typed in the search box finds entries that only contain it in Persian.
- The two halves of the result card are painted identically. The English half used to sit on a different background and border, which read as a third, unlabeled section; both halves now share one surface and differ only in direction and font.
- Editing a library entry is a real editor: «ویرایش» opens a wide dialog with the full request in a large RTL box, the Persian and English prompts side by side, and title and tags above them. The old inline row only offered a single-line box for the title and tags — a saved 2,000-character request could not be corrected at all. `PATCH /library/{id}` now accepts `input`, `purpose`, `persian_prompt` and `english_prompt` next to `title`, `tags` and `favorite`, with the same emptiness and 20,000-character guards as saving, and it still refuses to rewrite `id`, `created_at` or the stored analysis. A title the program derived from the request follows the edited request; a title you typed yourself is kept.
- Conversion now shows a real processing state. While a request is in flight a MAPSIM-branded sheet covers the workspace: the logo between two counter-rotating arcs, a four-step strip (خواندن درخواست ← ارسال به مدل ← ساخت پرامپت ← آماده‌سازی خروجی), one plain-Persian stage sentence that advances as the call ages, a live elapsed counter, the input length and the model name, and an indeterminate sweep. It is honest by construction: the fourth step only lights up once the answer has actually arrived, the late-stage messages say "still waiting" instead of inventing progress, `Esc` cannot dismiss it, and the page behind is `inert` so a second click cannot start a duplicate call. Below 520px of viewport height it compacts to fit a landscape phone, and under reduced motion the sweeping bar is dropped rather than left frozen.
- The 20,000-character ceiling is now visible instead of being a surprise. The counter under the request box states the limit next to the live length (`۰ نویسه · سقف ۲۰٬۰۰۰`) and both counters — the workspace one and the library editor's — turn red and bold the moment the text passes it, a frame before the app refuses the request. The number comes from `MAX_INPUT_LENGTH`, so it cannot drift from the real guard, and the over-limit toast formats its own number through the same Persian digit helper as the rest of the interface.
- Responsiveness: no horizontal overflow at 360px or wider (the model selector was pushing the page sideways once its option labels grew), every tap target is at least 44px including the library favorite button, and the model selector shrinks and clips instead of stretching. The four links that sit in running text (the API-key help, the pricing help inside both the model block and its list, and the footer API guide) measured 19–21px tall — too small for a thumb — so they now carry inline vertical padding that widens the tap area to 44–47px without moving a single line of text.
- One command runs the whole project on macOS, Linux and Windows. `./run.sh --host 127.0.0.1 --port 8000` and `.\run.ps1` find a Python 3.10+ interpreter (with install hints when there is none), build `.venv`, install the pinned requirements, start the server and print the address — no manual venv, no pip step, no editing of `main.py`. `run.bat` is a thin wrapper that hands every argument to `run.ps1`, so the launch logic lives in exactly one Windows script. Both launchers share one contract: the same minimum version, the same `.venv`/`requirements.txt` pair, the same `prompt_compiler.app:app` target, the same `PROMPT_STUDIO_*` environment variables and the same `127.0.0.1:8000` defaults, and `tests/test_http_api.py::LauncherContractTests` fails if the two files ever drift apart.
- The launchers are careful with the operator's machine: they never delete an existing `.venv` (a broken one is renamed `.venv.broken` and you are told), they reinstall only when `requirements.txt` has changed (a `.venv/.requirements.sha256` marker), they refuse to start when something already listens on the port instead of silently replacing the server you were looking at, they warn when asked to bind beyond loopback, and they never read `config.json` — the stored API key is not touched, printed or passed through the shell.
- Tests, CI and repository hygiene for GitHub: `./run.sh --tests` and `.\run.ps1 -Tests` run the suite inside the project venv, `.github/workflows/ci.yml` runs both launchers on ubuntu/macos/windows at Python 3.10 and 3.13 and then fetches the page, the catalog and every static asset from the server they started, a `static` job runs `node --check` and `compileall` and fails the build on a committed `config.json`/`usage.json`/`library.json` or an `AIza…` key pattern, and `.gitattributes` keeps `run.sh` LF and `*.bat`/`*.ps1` CRLF so the scripts work after clone on all three systems.
- `README.md` is now the full GitHub front page: an English and a mirrored فارسی guide, a facts table, the request-flow diagram, per-OS one-command install, what the launcher does, every CLI flag (including Windows-only `-VenvDir`) and environment variable with its default, the complete HTTP surface (methods, paths, status codes, limits), the layout tree, testing and CI, data-file permissions, a 14-row troubleshooting table mirrored row for row in Persian, and the licensing notes. Each troubleshooting row quotes a message the code actually prints, checked against the launcher and route source lines rather than paraphrased.
- Fixed a launcher argument bug found by running it: `./run.sh --python /nonexistent/python3` printed an empty interpreter name and a duplicated generic "Python is required" block, because the failure message was raised inside a `$(…)` subshell. An explicitly requested interpreter is now validated in the parent shell and reported precisely; `run.ps1` mirrors the behaviour.
- Tests: 111 in-process tests — 55 prompt-engine, including a new bilingual-mirror suite, and 56 HTTP/library/UI/launcher-contract. No socket and no provider call.

## 2.1 — prompt library, themes and a responsive workspace
- Added the prompt library: save a compilation with tags and favorites, search it, filter by tag or favorite, edit the title and tags, reload it into the workspace and delete it. Stored locally in `library.json` with owner-only permissions and a 500-entry working set.
- Added library endpoints `GET/POST /library`, `PATCH/DELETE /library/{id}` and wired them into the application.
- Shipped a light theme next to the existing neon dark theme, driven by one CSS token layer. The choice is remembered, applied before first paint, and follows the OS preference until the operator overrides it.
- Rebuilt the shell for every device size: the page scrolls normally instead of being clipped, the usage panel docks as a real column at 1000px and wider and slides in as an overlay below that, and the library becomes a full-height sheet on phones.
- Rebuilt the settings modal and the usage panel: masked key state, blank-means-keep with an explicit remove option, per-model RPM/TPM/RPD meters and readable empty and error states.
- Accessibility and keyboard: skip link, labeled controls, `aria-live` output, focus trapping and `Esc` precedence in dialogs, 44px touch targets, `prefers-reduced-motion` and `prefers-contrast` support, and AA contrast in both themes.
- Request guards: a shared 20,000-character input limit is enforced in the browser and on the server for both `/translate` and `/library`, non-text payloads are rejected, and usage polling stops when the panel is closed or the tab is hidden.
- Security: the API key is never rendered into the page, is sent through the `x-goog-api-key` header only, can be supplied through `PROMPT_STUDIO_API_KEY` / `GEMINI_API_KEY`, and stored files are written atomically with `0600`. `main.py` binds to `127.0.0.1` by default.
- Tests: added `tests/test_http_api.py` covering the page, catalog, usage, settings, translation guards and library CRUD — 87 tests in total, all in-process with no socket and no provider call.
- Documentation: README, architecture, security, release checklist and both user manuals updated for the library, themes and responsiveness.
